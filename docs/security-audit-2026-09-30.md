# OFF-ROUTE privacy and security review — 30 September 2026

The tested Supabase trip files were not publicly readable. However, the complete development setup should not yet be called safe to expose or share wholesale. Local recordings/backups, network-facing development defaults, and the optional legacy API need hardening. This review is a current assessment, not proof that historical unauthorized access never occurred.

**Live checks and safeguards**

- Tested a known existing trip's completion marker and raw recording chunk through both public and authenticated Storage URLs, with no credentials and with only the public app key. All eight file reads failed with HTTP 400; no file content was returned. The same files returned HTTP 200 using the owner's normal app login. This positive control distinguishes access denial from a nonexistent test file.
- Key-only listing of the journey root, user folder, session folder, model bucket, and bucket catalog returned zero visible entries. The owner's root listing returned one folder. The authenticated model bucket listing was empty. Anonymous REST schema access returned HTTP 401.
- The live dashboard showed three journey policies (SELECT/INSERT/UPDATE, authenticated) and one model policy, with no other storage.objects policies listed. The live journey SELECT expression requires the first path component to equal auth.uid(). The checked-in migration supplies the matching user-prefix rules for INSERT/UPDATE and authenticated model reads.
- Registration is enabled and email auto-confirmation is disabled. The Supabase Security Advisor showed zero errors and one warning: leaked-password protection disabled.
- Android Supabase traffic requires HTTPS and disables redirects. Session credentials use Android Keystore AES-GCM; the laptop refresh token uses Windows DPAPI. Contribution defaults off, with guards for consent/account changes. Android backup is disabled, and the recording service and file provider are not exported.
- No analytics uploader or external map/search service was found in the reviewed application source. Recorded trips intentionally upload to Supabase when contribution is enabled. Uploads contain location/sensor data; they are not end-to-end encrypted by this application. Authorized administrators/service credentials can access the server copies.
- Both production-only and full npm dependency audits returned zero known vulnerabilities at review time. A focused scan of 579 relevant text files found no recognizable privileged Supabase secrets, private keys, GitHub tokens, or JWTs. This is not an exhaustive binary/archive/history secret scan.

**Findings and fixes to prioritize**

| Priority | Finding | Evidence and consequence | Recommended action |
|---|---|---|---|
| High when a development server is reachable | Development commands bind to all network interfaces; sensitive workspace folders are not denied by the Vite configuration. | `package.json:11`, `vite.config.ts:9`. The watch ignore list only controls filesystem watching. It does not protect files from HTTP requests. | Bind to loopback by default and explicitly deny artifacts, recovery, uploads, data, credentials, and environment files from development serving. |
| High if the whole project is shared | Real recordings and recovery backups are eligible for accidental Git/source sharing. | `.gitignore` excludes the laptop-agent directory but not `artifacts/sept29-navigation/logs/` or `recovery/`. Examples include DRLOG/fusion recordings, a phone backup archive, and exported browser storage with recent places. No Git remote was configured and no publishing was observed. | Keep sensitive outputs outside shareable source; add targeted ignore rules and use an allowlisted export. Do not zip/share this entire workspace. Git ignore rules do not protect an ordinary ZIP. |
| Medium; optional legacy server | Development API can run without authentication; configured API keys grant shared access to all legacy trips. | `server/src/app.js:43`, `:73`, `:149`, `:164`; `server/src/index.js:12` binds 0.0.0.0. Production startup requires separate phone/admin keys, but does not add per-user trip isolation. | Disable the legacy API if unused; otherwise require authentication in every mode and enforce per-user ownership. This is separate from the protected Supabase path. |
| Medium; optional legacy upload | Legacy backend URLs allow HTTP and the workspace key is stored in browser localStorage. | `src/api.ts:14`, `:21`; `src/App.tsx:79`, `:156`; debug manifest permits cleartext. Remote HTTP can expose trip uploads and the API key to network interception. | Require HTTPS except explicit loopback development and move device credentials to encrypted storage. |
| Medium; account hardening | Supabase leaked-password protection is disabled. | Live Security Advisor warning. This means compromised-password screening is off; it does not mean your password has leaked. | Enable the protection if available for the project plan; use unique passwords and protect administrator access with MFA. MFA status was not verified. |
| Medium; device distribution | Default Android build scripts produce a debug APK. | `scripts/build-android.ps1:12`; merged debug manifest has debuggable=true. An authorized local debugger can read private application data. | Share signed release builds with debugging disabled. This finding does not establish an Internet leak. |
| Low; stolen-session response | Phone sign-out removes the local session without calling server-side logout. | `CloudSessionStore.java:167`. A previously stolen refresh token would not be revoked by this local sign-out. | Add server-side revocation where available, preserving local cleanup on failure. |

Published model binaries are intended to be readable by every authenticated app user under `offroute_model_read`, while trip recordings remain user-scoped. A public/publishable API key embedded in an APK is expected; protection must come from authentication and row-level policies. See [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys) and [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

**Scope and limits**

Reviewed the Android/frontend cloud and legacy data paths, laptop credential/downloader handling, Supabase migration and live policy display, storage access responses, development/deployment defaults, sharing exclusions, and npm advisories. No phone was connected, so the installed APK/settings and actual phone network traffic were not inspected. No second account was available for a live cross-account test. No uploads, account creation, deletion, policy changes, production release, or server configuration changes were performed. The saved app login was refreshed normally for owner-read checks.

No pre-existing listener was found on the usual app/database ports (3001, 5173, 4173, 27017) during the local review. Router/firewall forwarding, organization membership, signed links, backups, historical access logs, and Python/Android dependency advisories were not fully audited. Do not infer that the entire Internet exposure history or every dependency is clean.

Reproducible probe: `scripts/audit-cloud-access.py`. Sanitized results: `artifacts/security-audit/cloud-access.json`, `npm-audit.json`, and `npm-audit-all.json`. The probe prints status/counts only, never tokens or recording contents.

Until hardening is complete, share only the intended model files or a reviewed release APK, keep development services off shared networks, and keep recordings/backups private. Disabling Cloud contribution stops future automatic contribution; it does not delete trips already stored in Supabase.
